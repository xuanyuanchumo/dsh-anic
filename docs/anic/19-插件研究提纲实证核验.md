# 19 · 《插件研究.md》提纲实证核验

> 核验对象：`docs/插件研究.md`（40,829 B，12 章，未入库的提纲性文件）。
> 核验基准：dsh-anic `0.36.0`（git HEAD `3e81e8b`，cycle-37）的**真实代码与真实运行工件**。
> 核验方法：逐章提取提纲主张 → 在 `src/`（145 个 .ts / 16,632 行）、`tests/`（106 个 .ts / 15,083 行 / 1,190 个 `it(`）、`assets/skill/`（65 文件 / 16 脚本）、`.cycles/`（37 个 cycle 目录 / 108 条账本）中找对应物 → 给出判定与证据。
> 判定词汇：**已实现**（有可执行代码且被测试/工件覆盖）｜**部分**（有骨架但能力不完整）｜**未实现**（零代码）｜**与实现冲突**（提纲主张与仓库的既有裁决相反）。

---

## 0. 一句话结论

《插件研究.md》是一份**目标形态**的架构蓝图，而不是对本仓库现状的描述。它规划的知识图谱层、知识边界三原则、OTel span 树、Prometheus 指标、血缘对象图、拓扑指标、负向记忆、离线重放门禁，在本仓库 **一行代码都没有**；它点名的第三方包中，本轮联网核验的 52 个里 **23 个在 npm 查无此包**。而本仓库真正领先的东西（哈希链账本、五流程双实现差分守卫、fail-closed 的 `doubt` 三态、证据接地过滤、L1-L4 授权带 + 8 熔断）在提纲里只被零星提及，甚至被提纲的「自行实现」倾向判为可替换件。

**因此：提纲可以当作路线图读，不能当作设计依据读。** 它的生态部分（2.2 节 ~30 个第三方插件）需要先做存在性核验再谈选型。

### 第二章 · 技术基座选型

提纲主张：官方只维护框架运行时与核心插件骨架，第三方当参考实现，核心流程状态机/门禁裁决/知识边界若无可维护基座则「自行实现或深度 fork」。

**仓库实证与提纲在此处高度一致，而且走得更彻底**：

- `package.json` **零 runtime dependencies**——没有 `dependencies` 字段。只有 `peerDependencies`（`@deepseek-ai/cordis ^4.0.1` + 可选 `@deepseek-ai/dsh`）与 `devDependencies`（react/typescript/vitest/tsdown/jsdom 等 9 项）。

即：**本仓库从未引入任何第三方 DSH 插件**。提纲的「选型策略」在本仓事实上已经被执行成了「全部自研」。

### 第三章 · 核心架构分层

提纲提出 Client/Host 双面 + 6 层（流程状态机 / 算法引擎 / 评审门禁 / 知识层 / 自进化 / 透明化 + 自举层），并给出贯穿原则：「**状态机是硬边界，算法引擎是可替换的决策辅助，评审体系是带证据生命周期的裁决层；自主性来自被授权的选择空间，而不是无边界的自由**」。

**这条原则是本仓已经实现的**，且有代码级对应：

| 提纲层 | 仓库落点 | 实证 |
|---|---|---|
| 流程状态机（硬边界） | `src/host/flows/machine.ts` + `registry.ts` + 5 描述子 | `applyTransition` 是唯一写点且不落盘；`findTransition` 具体边优先于 `from:'*'` 通配；守卫按名查找，**未知守卫名 = 拒绝（fail-closed）**；`replayEvents` 对 `from ≠ 当前态` 的事件计入 `rejected` 不推进 |
| 算法引擎（可替换） | `flows/gateEngine.ts` + `gateCheckRunners.ts` 的 script/native/diff 三模式 | 「同一判定两条实现路径 + 差分对账」= 提纲「可替换」的更强形态 |
| 评审门禁（证据生命周期） | `llm/multiAgentGate.ts` + `multiAgentTier2.ts` + `gateEvidence.ts` | `SELF_REFUSAL` 常量；`evidenceIds` 接地过滤；`grounded.length===0 && approve` → 强制降 `doubt` |
| 知识层 | **无** | grep 全 0 |
| 自进化 | `evolution/` 16 文件 | 见第九章 |
| 透明化 | 客户端 12 分区 + 14 端点轮询 | **不是**结构化事件 + OTel span，是轮询 + 快照投影 |
| 自举 | `selfBootstrap.ts` + `bootstrapOrchestrator.ts` + `dualBootstrap.ts` | 有循环，但中间态空转（doc18 P1-6） |

**架构判定**：6 层里 5 层有实体，**知识层整层缺失**。提纲的「图谱主导 + 文本兜底」在本仓没有任何对应物，连「文本兜底」都没有——`assets/skill/references/` 15 个 md 是给人/模型读的静态文档，不是被检索的知识库。

### 第四章 · 流程状态机基座 `dsh-state-graph`

提纲主张直接采用第三方 `dsh-state-graph`（`addNode`/`addEdge`/`addConditionalEdge`/`addApprovalGate`/`addSubagent`、纯函数增量补丁 `Partial<State>`、**迭代熔断默认 25 次**、checkpoint 写 `ctx.fs`、参考 XState 的决策空间约束）。

**仓库实证：自行实现，且 API 形态完全不同。**

- 自研内核 `src/host/flows/machine.ts`：`validateDescriptor(d): string[]`、`findTransition(d, state, trigger)`、`canTransition(d, guards, state, trigger, gctx): GuardResult`、`applyTransition(...): FlowApplyResult<S>`、`initRuntimeState(d, now)`、`replayEvents(d, events, now): ReplayResult<S>`。
- 无 `addNode/addEdge/addSubagent`——转移是**描述子里的静态数组**，不是运行时增量构建。
- **无 25 次迭代熔断**。实际熔断阈值是 `DEFAULT_MAX_RETRIES = 3`（`src/host/evolution/autoFixEngine.ts:31`）与 `MAX_RETRIES = 3`（`src/host/evolution/fixLoop.ts:11`）；终态 `converged ? 'PASS' : round >= maxRetries ? 'EXHAUSTED' : 'FAIL'`（`fixLoop.ts:128`）。
- **无 `ctx.fs`**：全仓 `ctx.fs` 命中 0；持久化走 `node:fs`（55 个文件 import）+ `src/shared/fs-safe.ts` 的 `atomicWriteFileSync`。
- **无 subagent 状态机节点**：`subagent`/`Subagent` grep 命中 0。

**判定：与实现冲突。** 提纲的第四章若被当作设计依据，会要求引入一个本仓刻意不引入的依赖，并改变已经通过五套差分契约守卫的内核形态。仓库既有裁决（doc18 §5 negative space）明确「不做五注册表、不做子 fiber 常驻循环」——同一条纪律应覆盖第四章。

### 第五章 · 知识层（图谱主导 + 文本兜底 + 知识边界三原则）

这是提纲篇幅最大、也是本仓缺口最大的一章。提纲要求：
- 5.4 知识边界三原则：**真实支撑**（原文锚点/字符偏移/源文件哈希，锚点失效标记过期）、**孤例不证**（至少 2 独立见证或 1 最高可信层 + 人工批准，同源折叠）、**找不到不等于不存在**（`ok`/`low_confidence`/`absent`/`degraded` 四态，`absent` 必附扫描范围 + 计数 + 索引健康）。
- 核心立场：「边界靠确定性代码在写入和消费两端执行可审计检查，而非模型声明『我确认了』」。

**仓库实证：全部未实现。**

- 知识图谱 / 向量 / 混合检索 / RRF：`knowledge`、`graphmemory`、`embedding`、`bm25`、`rrf`、`retriev` 在 `src/` 全部命中 **0**。
- 原文锚点 / 字符偏移 / 源文件哈希：`anchor` 在 `src/` 6 处，全是 DOM 锚（`anchorKey: 'data-anic-steptrace-wrap'`）；`sha256` 20 处全在 `ledger.ts` 哈希链、`skillIntegrity.ts` 安装清单、`reviewEngine.ts` prompt 摘要、`selfCheckRoute.ts` 快照 digest —— **没有一处是「文档原文 → 内容哈希」**。
- 四态词表：`degraded` 在 `assets/skill` 与 `src/` 均 0 处（客户端有 `'pass'|'fail'|'doubt'|'warn'` 四态，但语义是裁决态不是知识置信态）。
- 「孤例不证 / 独立见证」：全仓 `独立见证` 命中 0。
- 唯一的弱替代物：`src/host/governance/factBaseVerify.ts` 的 `extractDeclarations`（正则抽 `F/N/A-数字` 声明 id）+ 源码扫描。它验证「声明过的东西有没有代码」，**不验证「代码说的依据是否真实存在」**，也没有「找不到 ≠ 不存在」的四态区分——`found: false` 直接被当成 missing 计数。

**判定：未实现。** 提纲第五章的立场（确定性代码在两端做可审计检查）与本仓的哲学完全一致，但**这一层的能力为零**。若要落地，建议先做最小闭环：`{docPath, anchorText, charOffset, sourceHash}` 四字段 + `ok/stale/absent` 三态 + 消费端强制「`absent` 必须附扫描范围」，而不是先做图谱。

### 第六章 · 自主决策

提纲主张 `@kasenri/dsh-orbit` Supervisor + MoA 多候选、工具白名单按阶段授权、产物模板与断言绑定、`dsh-proactive` 自主心跳**默认关闭**。

**仓库实证（逐项）**：
- Supervisor / MoA 多候选：**未实现**。`MoA` grep 0；`candidate` 25 处全是 DOM/路径候选变量名（如 `WorkflowTabIntegration.ts:85` 的 `const candidate = value as Partial<SlotsApi>`）。

- 自主心跳默认关闭：**无对应物**（本仓无主动心跳机制，全仓 `proactive` 0）。

**判定：部分。** 且「白名单声明但不强制」是本仓一个**真实存在的 P0 级缺口**——INV-28 的 `SELF_REFUSAL` 只在授权带（`autonomyBand`）维度生效，工具维度不生效。

### 第七章 · 三道门禁

提纲：产物质量（`dsh-eval-harness` YAML 用例 PASS/WARN/FAIL + CI 退出码）、离线重放（`dsh-plugin-veriscope`，**REVIEW 永不转 PASS**）、结构性（`dsh-autofork` 的 `gate.mjs`：注入完整性 + 参数文档不漂移）。裁决优先级：**确定性机械检查 → 结构化断言 → LLM 语义评审**。

**仓库实证：三道门禁全部自研，且与提纲的三分法不完全同构。**

| 提纲门禁 | 仓库对应物 | 差异 |
|---|---|---|
| 产物质量（YAML 用例） | `flows/gateEngine.ts` 的 G0-G3 + `checkQualityGate`；判据从**工件文本解析**（`gateArtifacts.ts` 的 `TASK_STATUS_RE=/^(待办|进行中|完成)$/`、`parseTestSummary`、`parseQualityRow`） | 不用 YAML 用例表，用固定工件契约 |
| 离线重放 | **无**（`dsh-plugin-veriscope` 未引入；`replay` 25 处全是状态机投影重算） | 缺整道门 |
| 结构性 | `scripts/validate-dsh.mjs` 12 检查（C1-C12）；`tests/contract/` 14 个契约测试含 `independenceGuard`（禁 import 父项目 src）、`toolOutputContract`、`dshConformance` | 有，但检查项不同（本仓查 DSH 清单合规 + 独立性，不查「注入完整性」） |

**裁决优先级**：仓库**已经实现且更严格**——`src/host/llm/gateEvidence.ts` 注释原文：「未出现在账本中的收敛门 → FAIL（『从未记录过』不等于『通过』）」；`verifyLedger` 对空账本返回 `{ok:true,total:0}`，插件侧刻意改判 FAIL，理由「0 条即无证据，按 INV-23『没有证据 ≠ 通过』判 FAIL」。Tier-2 LLM 评审的证据接地（`multiAgentTier2.ts:119` `const grounded = verdict.evidenceIds.filter(id => allowed.has(id))`）保证 LLM 不能凭空 approve。

**判定：部分（2/3 门禁已实现，离线重放门缺失）。** 但仓库在「证据不足即 FAIL」上比提纲更彻底——提纲的 `REVIEW 永不转 PASS` 在本仓已经泛化成「`doubt` 永不转 PASS」。

### 第八章 · 评审三层

提纲：`7d-code-reviewer`（五步/三级严重度/四维评分）、`dsh-model-everything`（断言即可执行模型，结论带出处与哈希）、`dsh-jev-gate`（「目录是数据，不是代码里的 if」，未登记工具默认不过闸）+ `dsh-negative-ledger`（precondition 变化 → 结论 stale）。

**仓库实证**：
- `7d-code-reviewer`：**未引入**（npm 无此包）。
- `dsh-model-everything`：**未引入**（npm 存在 0.1.0）。
- `dsh-jev-gate` / `dsh-negative-ledger`：**均未引入，且 npm 无此包**。
- 本仓自己的三层是：**Tier-1 确定性**（`gateEngine` + `heuristicReview`，后者在零证据时返回 `doubt` 并诚实标注 `tier:'tier-1-heuristic'`）→ **Tier-2 LLM**（`multiAgentTier2.ts`，`ctx.llm` 探测、闭合 JSON 校验、接地过滤、逐角色独立降级）→ **契约套件**（`tests/contract/` 14 个，离线自评审）。
- 「结论带出处与哈希」：**部分**。`reviewEngine.ts:88-110` 的 `promptDigest`（sha256 前 16 位）只摘要提示词，不摘要结论依据。

**判定：部分（三层自研齐全，但缺「结论 staleness」与「断言即模型」两个机制）。**

## 2. 三个结构性发现

### 发现一：提纲的「生态吸收」路线在本仓已被反向裁决

提纲第二章主张「第三方当参考实现」，第五至十章大量引用第三方包作为机制来源。但：
1. 本仓 **零 runtime 依赖**，从未吸收任何第三方 DSH 插件；
2. 提纲点名的包中 **23 个 npm 查无此包**（本轮核验 52 个），包括 7 个被当作核心机制来源的（`dsh-autofork`、`dsh-negative-ledger`、`dsh-plugin-topology`、`dsh-lineage`、`dsh-event-auditor`、`dsh-jev-gate`、`7d-code-reviewer`）；

→ **建议**：提纲第二章需重写为「存在性核验 + 逐包判定」，否则后续任何按提纲选型的工作都会踩空。

### 发现二：缺口高度集中在「知识层」，其余是形态差异而非能力缺失

把 12 章映射到能力域：

| 能力域 | 判定 | 证据密度 |
|---|---|---|
| 流程状态机 / 门禁 / 评审 | **强于提纲** | `tests/contract/` 14 契约 + 1240 用例 + 五套差分对账 |
| 自进化提案 / 自举循环 | 部分 | 有循环无执行 |
| 透明化 | 形态不同、能力相当 | 工件投影 vs 事件溯源 |
| **知识层（图谱 + 边界三原则）** | **零** | grep 全 0 |
| 生态吸收 | 反向（零依赖） | — |

→ **建议**：提纲的第五、六、八、十章的「知识/记忆/血缘」相关机制应合并成**一个**独立项目立项，而不是散落在四章里。它是唯一需要从零开始的整层能力。
