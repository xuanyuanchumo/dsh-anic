## 2. 内部技能库：从「零引用」到「被读且可判红」

**修前**：`assets/skills/`（1 主干 + 9 叶 + 1 元技能 + 注册表 + 三脚本）在 `src/` 里**零引用**；
闭环体检第四族只扫 `assets/skill/scripts/*.mjs`（主干脚本），整个库不在扫描面内
（`closureAudit/skillClosure.ts:33`）。⇒ 库是否完整只能靠人记得跑 `skill-lib-manifest.mjs`。

**落地**：

| 落点 | 内容 |
|---|---|
| `src/host/pluginRoot.ts` | `pluginAssetDir` 增 `'skills'`（内部库根） |
| `src/host/runtime/skillLibrary.ts`（新增） | **只读**对账：注册表 ⇄ 目录 / `SKILL.md` / `anchors`，**反向**查未登记目录；六种 `issue.kind` 分流；5s 缓存（4s 轮询面防 fs churn） |
| `src/host/routes/skillHealthRoute.ts` | `GET /anic/skill/health` 增 `runtimeSkill` 与 `library` 两段 |
| `src/host/toolsStatusGateway.ts` | `anic_status` 增 `runtimeSkill`/`skillLibrary`（LLM 面：模型能看到「库有几条、有没有问题」） |

**首跑即抓到的真实缺陷**：`skills.index.json` 的 10 条里 **9 条缺 `dir` 字段**
（只有 `_meta/skill-library-evolution` 有）⇒ 任何按注册表遍历的工具只能识别 1 个技能。
**决策：不从 `name` 派生 `dir`**（注册表是唯一事实源，派生会让「表缺字段」永久隐身）
⇒ 报 `registry-parse` 逼人补表，并由契约在真实库上断言 `issues === []`。

**验收**：`tests/unit/skillLibrary.test.ts`（11 用例，六种 issue 各一条会判红）+
`tests/contract/skillLibraryRegistryContract.test.ts`（真实库全绿 + `src` 真的读了注册表 + 路由真的消费）。

## 3. 三态而不是布尔（本轮的统一裁决）

三个新裁决面（披露 / 技能可见性 / 库对账）**都**是三态或带 kind 的多态，理由同一条：

| 面 | 三态 | 为什么不能合并 |
|---|---|---|
| 披露 | `verified` / `partial` / `unverified` | `partial` 可能是**越权泄漏**（要收紧）也可能是**自锁**（要放宽）；`unverified` 只是采不到 |
| 技能可见性 | `active` / `absent` / `unknown` | `unknown`（观测不完整）谎报成 `absent` 会让工作区安装态被误判成缺失 |
| 库对账 | 六种 `issue.kind` | 补救动作不同（补文件 vs 改表 vs 修 JSON） |

## 5. 本轮不做（防漂移，与研究输入 L §6 一致）

| 项 | 理由 |
|---|---|
| R3 每会话 FIFO 调用预算（L §4 建议 3） | 改变并发语义，需一轮经验证据；本仓纪律「默认零行为变更」。留作 opt-in 候选 |
| `assets/skills/` 改 `registerProvider` | 要实现 `list/get/rank/locator/signal` + watcher/失效，属**新子系统**。先把回读通路与读数打通 |
| `availability: resident\|discoverable` | **不是官方字段**（KB `tools.md:31-107`），宿主不读；加了就是「声明无消费方」 |
| 抄 ops 的 `tools.view()` | 不在 KB 任何页面；本仓无 `schemas()` 深拷贝成本，唯一读面用文档化 `schemas(scope)` |
| merge `ledger.ts` / `segmentedLedger.ts` | 双写者协议变更，需先有差分取证轮 |
