# DSH 原生流程插件：从技能到自治知识系统的完整整合方案

下面把此前分散讨论的选型、架构、门禁、进化、透明化与知识层设计，整合为一份**可直接作为需求文档骨架**的完整方案。


## 一、项目定位与总体目标

将现有的“开发流程技能”改造为**原生 DSH 插件**，使其具备：

1. **全生命周期流程管理**：设计 → 实现 → 自测 → 评审 → 归档，阶段状态可持久化、可审计、可回滚。
2. **流程可视化与透明化**：泳道看板、事件流、会话回放、拓扑视图，所有流向可追溯。
3. **知识层赋予**：以知识图谱为主导、文本/向量检索为兜底，在阶段边界自动检索与沉淀。
4. **自主评估决策**：模型在状态机约束内自主选择阶段、工具与产物方案，而非无边界自由循环。
5. **门禁测试**：阶段迁移前强制通过产物质量、离线重放、结构性三道闸门。
6. **自进化与自举**：根据失败信号与门禁结果改进自身资产；运行中发现能力缺口时自行生成并挂载新插件。
7. **知识边界验证**：每条知识必须满足“真实支撑”“孤例不证”“找不到不等于不存在”三原则。
8. **数据、流程、量化全透明**：结构化事件为唯一事实源，指标、追踪、血缘图共享同一份原始数据。


## 二、技术基座选型：官方与第三方的真实边界

### 2.1 官方提供的底座

DSH 官方直接维护的只有**框架运行时与核心插件骨架**：

- `deepseek-ai/deepseek-harness` 仓库、Agent Loop 核心、Cordis 依赖注入体系
- `create-dsh-plugin` 脚手架（生成 `dsh.bundle`、`cordis.patch.yml`、Host/Client 双面结构）
- `dsh-agent-teams` 插件开发文档（Host 面 / Client 面协作范式）

官方对插件生态的治理投入非常有限——基本只有“给你的仓库打上 `dsh-plugin` GitHub 标签”这一句话。**因此“官方”不能作为第三方插件的安全背书。**

### 3.2 贯穿性设计原则

**状态机是硬边界，算法引擎是可替换的决策辅助，评审体系是带证据生命周期的裁决层。** 模型的自主决策、自进化和自举只允许在硬边界内部活动——**自主性来自被授权的选择空间，而不是无边界的自由**。

这与 `dsh-orbit` 把控制权留在 Supervisor、`dsh-auto-evolve` 的变异词汇表由代码定义、`VeriScope` 的 REVIEW 永不转 PASS 是同一种安全哲学。


## 四、流程状态机：声明式图内核

### 4.1 基座：`dsh-state-graph`

- **声明式拓扑**：`addNode` / `addEdge` / `addConditionalEdge` 构建多分支条件路由
- **纯函数增量补丁**：节点返回 `Partial<State>`，引擎不可变合并
- **迭代熔断**：默认 25 次迭代超限抛错
- **审批门**：`addApprovalGate` 请求 `ctx.approval` 一次性授权
- **子代理节点**：`addSubagent` 委托真实 DSH 子代理，输出映射回父状态
- **checkpoint 回调**：每次节点合并后写持久化到 `ctx.fs` 或 session log

### 4.2 决策空间约束

参考 XState 的 Agent 集成模式：**状态机拥有控制流，模型只提议事件，机器决定是否允许以及下一步是什么**。在条件边处理器内部做薄封装，把模型输出映射为**状态机已声明的事件枚举**，非法事件直接拒绝。

`dsh-per` 的 `transition-table.ts` 是状态迁移的唯一权威——所有迁移从统一出口发射，子模块不能绕过 FSM 直接改状态。

### 4.3 拓扑的角色

- **编排拓扑**：状态图本身就是有向图拓扑（节点、静态边、条件边、并行 Fan-out/Fan-in、子图嵌套）。默认**静态拓扑 + 条件边**，远期可评估可进化拓扑。
- **依赖拓扑**：用 `dsh-plugin-topology` 的图论指标（入度/出度、介数中心性、PageRank、密度、是否 DAG、直径）检查插件依赖健康度——循环依赖、单点故障、关键路径拥塞。
- **知识检索拓扑**：关系型知识用拓扑传播作为可插拔检索通道，与 BM25/向量并列，由 RRF 融合。

**降维/升维**：非架构必需品。仅在向量检索候选压缩（后置到指标可测之后）和多见证联合评审（超图等高阶表示）两个场景中按需引入。


## 五、知识层设计：图谱主导，文本兜底

### 5.1 为什么用知识图谱替代传统知识库

传统 RAG 知识库的核心是“分块 + 向量相似度”，擅长找相关文本，但不天然理解实体关系、多跳推理和全局结构。知识图谱把知识抽取为“实体-关系-实体”三元组，检索时沿图的边做多跳扩散或子图召回，能回答结构性、因果性、多跳问题。

### 5.2 推荐插件谱系

**通用记忆图谱**：
- `dsh-graphmemory`：TASK/SKILL/EVENT 三类节点，`USED_SKILL`/`SOLVED_BY`/`REQUIRES`/`PATCHES`/`CONFLICTS_WITH` 边，向量 + FTS5 双路召回，压缩上下文约 75%
- `dsh-advanced-memory`：分层 + 图谱 + 世界线版本 + 向量，k-hop 邻域扩散、BFS 最短路径、社区聚类
- `axiom-kb-dsh`：Vault 记忆 + 知识图谱，`kb__<tool>` 前缀

**文件原生图谱**（与透明化架构最契合）：
- `dsh-knowledgenet-plugin`：一个节点就是一个 Markdown 文件，节点间记前置依赖，图谱存 `.dsh_knowledge/graph.json`，边带“为什么 + 出处”，节点身份由 ULID 固定
- `conversation-knowledge-map`：只读、可筛选、可回溯来源的静态知识图谱，保留来源事件序号

**代码/文档结构图谱**：
- `dsh-plugin-knowledge-graph`：`CONTAINS`/`EXPORTS`/`IMPORTS`/`IMPORTS_SYMBOL` 关系
- `dsh-codegraph`：按符号、按区域查询
- `dsh-docs-reader`：ECharts 力导向图

### 5.3 图谱主导 + 文本兜底的务实策略

纯图谱替代知识库的最大风险是**抽取损耗**——叙述性、模糊性、多义性内容难以干净地抽成三元组。DSH 生态中成熟的图谱插件几乎都不是纯图检索。

**建议**：以图谱作为主导知识层和门禁的结构性依据，保留轻量文本/向量通道兜底。门禁的“真实支撑”检查优先沿图谱节点/边锚点进行；当图谱覆盖度不足（显式标记 `degraded` 或抽取队列积压）时，回退到带锚点的文本检索。

### 5.4 知识库边界三原则

| 原则                   | 门禁检查项           | 通过条件                                           | 不通过处理                    | 案例依据                                            |
| :--------------------- | :------------------- | :------------------------------------------------- | :---------------------------- | :-------------------------------------------------- |
| **真实支撑**           | 原文锚点存在性       | 每条知识带逐字引语、字符偏移或行级定位、源文件哈希 | 降级为候选或丢弃；转人工确认  | `dsh-memory-porter`、Kestrel、`dsh-socrates`        |
|                        | 锚点有效性           | 源文件哈希未变，引用行未偏移                       | 标记知识过期，阻断消费门禁    | Kestrel SHA-256                                     |
|                        | 引语长度与逐字一致性 | 引语达到最小长度且字面子串匹配                     | 拒绝引用                      | Kestrel 少于 24 字符拒绝                            |
| **孤例不证**           | 来源独立性           | 至少两个独立见证，或一个最高可信层级见证加人工批准 | 同源折叠为一个见证，不晋升    | Kestrel 独立确证评分、`dsh-obsidian-math`           |
|                        | 来源类型分级         | 社区来源不单独构成充分证据                         | 要求交叉验证或官方来源补充    | `dsh-deep-search`                                   |
| **找不到不等于不存在** | 检索四态裁决         | `absent` 必须附扫描范围、扫描计数、索引健康        | 空结果不得作为否定证据        | `jcodemunch` 的 `negative_evidence`                 |
|                        | 索引健康状态         | 索引正常才允许 `absent`                            | `degraded` 阻断门禁，等待修复 | `jcodemunch` 四态                                   |
|                        | 覆盖度声明           | 声明搜索范围与未覆盖区域                           | 未声明范围的否定结论拒绝      | `oak-open-curriculum-ecosystem`、`dsh-deepresearch` |

**核心立场**：知识库的“边界”不是靠模型声明“我确认了”来划定，而是靠确定性代码在写入和消费两个端点上执行可审计的检查来划定。模型的自我评估和自进化只允许在已被代码验证为合格的知识之上活动。


## 六、自主决策、工具选择与产物生成

### 6.1 决策层：Supervisor 约束内自主

`@kasenri/dsh-orbit` 的核心设计：**把真正的流程控制权留在 Supervisor，而不是交给模型自由循环**。规划、执行、审核、纠错、恢复、最终验收拆成明确角色，由确定性 Supervisor 驱动，模型只在被授权的决策点上做选择。

**MoA（多候选执行）** ：关键步骤存在多种合理实现路线时，多个 Candidate 独立给出方案，Judge 相对选优。

`dsh-decision-router` 的置信度不足时回退确定性规则，可作为工具选择的安全网。

### 6.2 工具选择与产物生成

- **工具白名单按阶段授权**：当前阶段只允许调用已声明的工具集
- **产物模板与断言绑定**：产物必须包含必需字段与引用
- **生成前检索知识库，生成后记录产物来源**：产物可回溯到知识和工具调用

### 6.3 主动感知的克制使用

`dsh-proactive` 提供“自主心跳”机制：无外部任务时主动观察自身状态、发现瓶颈、生成改进目标。**默认关闭**，仅在显式开启的 profile 中启用，避免无人监管时自行发起不可预期动作。


## 七、门禁测试：三道互补闸门

### 7.1 闸门一：产物质量门禁——`dsh-eval-harness`

用 YAML 声明评测用例（prompt + 期望行为断言），headless 驱动真实 agent 跑 trace，对比 baseline 输出 `PASS|WARN|FAIL` 与 CI 退出码。`eval_gate` 直接作为流程状态迁移的前置条件——门禁不通过，状态机拒绝进入下一阶段。

### 7.2 闸门二：离线重放门禁——`dsh-plugin-veriscope`

“Python 是唯一数值裁判”的离线重放模式：把已有评测 JSON 接入 DSH，调用原 Python Quality Gate，返回通过/失败/待复核，强调 `REVIEW` 永不转为 `PASS`。适合高风险产物的第二道独立确认。

### 7.3 闸门三：结构性门禁——`dsh-autofork` 的 `gate.mjs`

两个早期失败门禁：**注入完整性**（`inject` 未声明的服务直接抛错）和**参数文档不漂移**（README 参数表与实现一致）。自进化产生变更后，先跑结构门禁，再进入行为门禁。

### 7.4 门禁裁决优先级

**确定性机械检查 → 结构化断言 → LLM 语义评审**，而不是反过来让模型“自信地宣称通过”。

`dsh-per` 的机械验证：compile、lint、tests 每轮重新执行，超时按 unavailable 处理，**reviewer 通过但机械验证失败时仍进入修复路径**。


## 八、评审体系：分层、可审计、可吊销

### 8.1 第一层：结构化审查（模板驱动 + 多维评分）

`7d-code-reviewer` 的评审协议：五步审查流程、三级严重度（critical/medium/minor）、四维度评分（代码质量/安全/性能/可维护性），输出文本摘要 + HTML 报告双格式。**模板与判定分离**：`SKILL.md` 决定审什么、多严重，`templates/` 只负责呈现。

### 8.2 第二层：断言即模型的可执行审查

`dsh-model-everything` 的核心理念：把设计与代码中的行为断言抽成可执行模型再判定。状态机、协议、数据模型先建成可运行模型，再交给引擎跑；结论带出处与哈希，可复算、可比对。当流程产物涉及行为变更时，评审不应只看文本描述，而应要求一份可执行的模型或断言集。

### 8.3 第三层：证据约束的门禁与负向记忆

`dsh-jev-gate` 的设计原则：“目录是数据，不是代码里的 if”，决策点和工具绑定声明在表中，新增工具是改表而非改门禁逻辑；**未登记的工具默认不过闸，而不是默认放行**。门禁套件包含类型检查、逻辑测试、宿主测试、客户端测试、契约检查、密钥检查和构建字节一致性。

`dsh-negative-ledger` 补上“评审失败之后”的环节：把已证伪的路径连同 outcome 见证（退出码、错误码）+ precondition 见证（文件状态）记录下来；**任一 precondition 变化 → 结论 stale，提醒自动撤销、允许重试**。


## 九、自进化与自举：验证即部署，人类保留否决权

### 9.1 自进化方案 A：`dsh-auto-evolve`——沙箱验证 + 版本账本 + 自动回滚

闭环：**Observe → Propose → Validate → Apply**。观察工具失败、重复调用、请求错误等信号，达到阈值后由 LLM 在**封闭的变异词汇表**内提议修改（`add`/`patch`/`retire` 作用于 skill/post-processor/prompt-section/guard-policy）。Validate 阶段在**全新沙箱 sub-agent 中重放失败 episode**，一次不带候选、一次带候选，**只有 trial 显示可测量的改进才 Apply**，每次变更记入版本账本，回归时自动回滚。**“验证即部署”** ——验证用的代码路径和实际应用路径是同一套。

### 9.2 自进化方案 B：`dsh-continual-evolve`——门禁驱动的持续沉淀

从会话轨迹中沉淀**版本化、可审计、可回滚的 harness 状态**（提示词/记忆/技能/子代理规格），带有审查门禁和 benchmark 闭环：候选沉淀先经**冻结用例 + 独立评分者**评估再接受，被拒候选自动沉淀为 draft 回归用例。**门禁的 FAIL 记录本身就是进化层的输入。**

### 9.3 自进化方案 C：`dsh-evolve-modes`——人类审查的“提议模式”

默认 Propose 模式，只提出候选规则，**不自动改变后续行为**，由人工审阅批准后才生效。生产环境或多人协作推荐此档位。

**三档设计**：Propose（提议）/ Sandboxed（沙箱验证后自动应用）/ Off，由流程 profile 显式选择。

### 9.4 自举：`self-iteration-forge`

AI 执行任务时发现能力缺口，调用 `extend_self`，由子代理把缺失能力锻造成插件——迁移为独立 git 仓库 → 自动装入当前 profile → **热挂载到当前会话**，无需重启。

**自举必须被门禁包围**：
- 子代理构建失败或加载冒烟不通过时 **throw 并保留 staging**，不静默降级
- 自举后强制跑 `dsh-eval-harness` 回归用例，**新能力通过门禁才允许进入正式流程**
- 自举生成的新插件默认**不自动获得写知识库权限**

### 9.5 分阶段启用建议

| 阶段     | 启用能力                                                     | 默认档位                                         |
| :------- | :----------------------------------------------------------- | :----------------------------------------------- |
| 第一阶段 | 原生插件基座、流程状态机、可视化面板、知识层挂载、产物质量门禁 | 全自动执行，门禁硬阻断                           |
| 第二阶段 | 自主评估决策、工具白名单、知识边界三原则检查                 | Supervisor 约束内自主，高风险人工批准            |
| 第三阶段 | 自进化 Propose 模式；缺席四态门禁                            | 只提议不自动应用；`degraded` 阻断                |
| 第四阶段 | 自进化 Sandboxed 模式（仅低风险资产）；受控自举              | 低风险自动应用，高风险人工批准；自举产物默认只读 |


## 十、透明化、可视化、量化

**核心思路**：结构化事件流作为唯一事实源，OpenTelemetry 标准做无侵入采集，分别投影为指标（量化）、追踪（流向可视化）和血缘图（数据透明化）。三者共享同一份原始数据。

### 10.1 量化：从事件流到可聚合指标

- **`dsh-prometheus`** ：观测 DSH 公开生命周期接缝，导出 Prometheus 指标 + Grafana 仪表盘，**不导出对话或工具 payload**。覆盖活跃会话数、agent turns/steps/errors 与耗时直方图、LLM 请求速率/延迟/token 计数、工具调用成功率与延迟、审批请求计数、子代理生命周期。
- **`dsh-telemetry`** ：请求耗时分解（模型/工具/插件/排队各占多少）、token/重试成本、最慢和最易失败的工具调用、缓存命中率、模型路由是否省钱。每个指标标注样本数，**可从原始事件重算**。
- **`@beibeihk/dsh-agent-observability`** ：从已提交会话证据重建 Session→Turn→Step→Model settlement→Tool call/result 轨迹，**零模型自报**，引用精确事件序号。

### 10.2 流向可视化：三个互补层次

**微观执行流（OTel span 树）** ：
- `@loongsuite/dsh-plugin`：每个 agent turn 转换为 GenAI span 树 `ENTRY → AGENT → STEP → LLM / TOOL`，每次真实 LLM 尝试有独立 span，工具调用通过 DSH call ID 与结果关联，子代理会话携带父会话属性，导出到 Jaeger/Tempo/SigNoz/Langfuse
- `dsh-observe`：同类方向，turn/step/tool/LLM spans 和 token/cost 指标导出到 OTLP 和 Langfuse

**中观过程流（时间线回放与事件审计）** ：
- `dsh-replay`：逐事件拖动 turn/step/消息/工具调用，1–16 倍速播放，点击任意事件看原始提示词/参数/结果/耗时；累计 token 曲线、工具耗时排行、分支树、规则化安全审计、会话对比；导出独立 HTML 回放
- `dsh-event-auditor`：监听 22 个 `emit` 和 10 个 `waterfall` 事件，按事件名与分发模式计数，环形缓冲保留最近 500 条，`/audit` 面板 + `/api/audit/events` JSON 接口

**宏观结构流（拓扑与依赖）** ：
- `dsh-plugin-topology`：插件/服务纤维树快照为二分图，导出中心性、密度、是否 DAG、直径
- `dsh-3d-plugin-graph`：实时 3D 拓扑渲染，节点和边都是真实运行时状态

### 10.3 数据透明化：血缘、因果与证据对象图

**`dsh-lineage`** 是当前生态中最贴近“数据透明化”的插件：
- 为 artifacts、verified-fact records、actions 和 reports 构建**本地可验证的对象图**
- 节点是类型化 ID + workspace 相对路径 + 预期 SHA-256
- 边是 `derived-from`、`observed-by`、`produced-by`、`supersedes` 等因果类型
- 验证器区分四种状态：`verified`（对象存在且哈希匹配）、`missing`（引用无法解析）、`stale`（对象存在但哈希已变）、`dangling`/cycle
- **没有任何缺失或过期的对象会被静默晋升为 fact**
- 账本 append-only，每个事件有幂等键，写入经过临时文件→读回→硬链接→再读回校验 SHA-256 的原子流程
- 所有路径 workspace 相对，拒绝遍历和符号链接；schema 只允许结构性 ID、类型、路径和哈希，**显式拒绝 chat、prompt、message、raw content、credential 等键**

**与知识边界三原则的对应**：
- “真实支撑” = 哈希可验证的对象引用
- “孤例不证” = 对象图的多独立来源需通过因果边验证，而非简单计数
- “找不到不等于不存在” = `missing` 和 `stale` 是显式状态，不是静默忽略

### 10.4 轻量补充

- `dsh-flowglass` / `dsh-dynamic-toolbox`：会话血缘树（Host-only）+ AI 旁路调用台账
- `dsh-whale-report`（深迹/DeepTrace）：把会话事件日志聚合成可读的诊断结论和改进建议
- `dsh-lifecycle-inspector`：插件生命周期健康诊断，哪些 Effect 注册了、哪个 Fiber 处于 `failed`/`pending`/`unloading`、teardown 是否超时

| **第三阶段** | 自进化 Propose 模式；缺席四态门禁；OTel 追踪 + Prometheus 指标 | 只提议不自动应用；`degraded` 阻断                | 候选变更队列、审计记录、回滚账本、Grafana 仪表盘             |
| **第四阶段** | 自进化 Sandboxed 模式（仅低风险资产）；受控自举；血缘图 + 拓扑健康检查 | 低风险自动应用，高风险人工批准；自举产物默认只读 | 沙箱验证报告、自举插件门禁回归结果、血缘对象图、拓扑指标基线 |

**贯穿原则**：状态机是硬边界，算法引擎是可替换的决策辅助，评审体系是带证据生命周期的裁决层。透明化不是增加一个仪表盘，而是确保每一个影响流程走向的动作都留下不可篡改的结构化痕迹，并且这些痕迹可以被独立重算和交叉验证。模型的自述、自然的日志文本、不可追溯的聚合数字，都不构成透明性。
