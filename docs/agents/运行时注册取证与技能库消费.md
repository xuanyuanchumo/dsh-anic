# 运行时注册取证与技能库消费（cycle-109）

> 本文回答四个问题：
> ① 我们**施加**了工具遮蔽之后，**宿主**真的少给了什么？
> ② 我们**注册**了 runtime 技能之后，模型**真的能看见**吗？
> ③ `assets/skills/` 那套内部技能库，**谁在读**？
> ④ 这三件事的读数**从哪查**、**怎么判红**。
>
> 全部事实从源码与官方 KB 读出，标注 `文件:行号`。无法验证的写「未验证」。

## 1. 为什么需要「取证化」（旧口径的缺口）

`src/host/runtime/disclosureReadout.ts` 的文件头长期写着诚实边界：

> 本模块**不证明**宿主的 `restrict` 真的按 deny 生效……只回答**我们这一侧**施加了什么。

于是 indexed 披露的「成功」长期是**信任态**：`wired:true` 只说明 `restrict()` 没抛。
同理，`src/host/skillRegistration.ts` 旧实现的 `log.info('已注册')` 是**无条件**的 ——
而官方语义里 **project 层同名技能会直接赢得 runtime 条目**
（KB `subsystems/skills.md`「本地发现优先级」）。工作区放一个同名
`.dsh/skills/<name>.md` 就能静默压制本插件技能，日志却照绿。

⇒ 本轮的共同修法是同一条：**把「我们做了什么」升级为「对方真的收到了什么」**，
并把结论放到**可读状态**而不是只进日志。

## 2. 工具面：`schemas(scope)` 取证与三态裁决

### 2.1 为什么是 `schemas(agent)`（A0″ 的白盒结论）

官方 KB `site/reference/subsystems/tools.md`：

| 锚点 | 原文（节选） | 用途 |
|---|---|---|
| `:512` | 「one visibility resolver feeds **presentation, lookup, and dispatch**」 | 三者共用**同一个**可见性解析器 |
| `:566` | `get(name, scope)`：「a restricted-away global reads as **absent**」 | A0′ 真机已证（视图 25→24） |
| `:574` | `schemas(scope)`：「one deep-cloned schema per **visible** tool」「the viewing scope (**the agent**); omitted = the **global view**」 | 取样必须传 agent |

A0′ 真机探针（`.cycles/tech-debt/cycle-73-a0-probe-result.md`）实测：
`scopedBefore:25 → scopedAfter:24`、`deniedHidden:true`、`getScopedAfter:"absent"`、
`globalUnaffected:true`。**同一个解析器**驱动 `get` 与 `schemas`
⇒ `schemas(agent)` 必然同样排除 deny 项。这就是 A0″ 的结论，**不需要再跑一次黑盒探针**。

> ★ 实现坑（A0′ 的 v7 踩过）：**`schemas()` 不传参返回全局视图**。
> 拿全局视图判 scoped 遮蔽会**恒报 partial**。故 `captureHostVisibility`
> 在没有 agent scope 时**拒绝采集**（判 `unverified`），绝不冒充。

### 2.2 三态判据（`src/host/runtime/disclosureVerdict.ts`）

```ts
classifyDisclosureVerdict(expectedVisible, observedVisible, deny)
  observed === null            → 'unverified'   // 采不到 ≠ 失败
  leaked = deny ∩ observed     → 'partial'      // 该遮蔽却仍在（越权暴露）
  missing = expected − observed→ 'partial'      // 该可见却不见了（遮蔽过头/自锁）
  两者皆空                      → 'verified'     // 正面结论，必须显式说出来
```

为什么**不合并** `leaked` 与 `missing`：两者的补救动作**相反**
（前者要收紧、后者要放宽）。合并成一个 `partial` 会让读者不知道该往哪边改
—— 与 `graphExtras.ts` 里 `unreachable`/`tooLong` 必须分开说是同一条纪律。

宿主**多给**的他人工具（既不在 expected 也不在 deny）**不计入**裁决：
本插件无权判定别的插件/宿主自带工具，多报会让裁决在他人工具上恒 partial。

### 2.3 接线顺序（不可反）

`src/host/toolDisclosureWiring.ts` 的 `applyDisclosureToScope`：

1. 注入索引 section（失败 ⇒ 中止，**绝不**遮蔽 —— 否则模型无检索通道 = 自锁）；
2. `restrict({deny})`；
3. **然后**才 `captureHostVisibility` 取证 —— 反序采到的是全量视图，裁决恒 partial；
4. 取证结果进 `WiringOutcome` 的 `hostVerdict` / `hostVisible` 并写入 agent 状态。

三条纪律：
- **取证是旁路**：`schemas` 缺失 / 抛错 ⇒ `unverified`，**绝不**因此回退 full
  （否则观测故障会升级成行为变更）；
- **一次/agent**（接线时 + 解锁时），不进轮询；
- **解锁后重采**：deny 变了，旧裁决已过期（`unlockTool` 内 `Object.assign(st, capture…)`）。

### 2.4 读数出口

`GET /anic/api/disclosure`（`src/host/routes/disclosureRoute.ts`）与
`summarizeDisclosure` 现在带：

```
agents=N, unlocked=M, fullyMasked=K, tools/change=X,
host=verified:a/partial:b/unverified:c
```

`AgentDisclosureReadout` 增加 `hostVerdict` / `hostVisible` / `hostLeaked` / `hostMissing`。
三态**分开计数**（`hostVerifiedAgents` / `hostPartialAgents` / `hostUnverifiedAgents`）——
把 `partial`（可能越权）与 `unverified`（只是采不到）混成一个「not verified」
会让真正的越权淹没在噪声里。

## 3. 技能面：注册 ≠ 可见（三态 + 调用策略）

### 3.1 调用策略贯通（frontmatter 两键不再被静默丢弃）

旧 `parseSkillFrontmatter` 只保留 `name/description/whenToUse`，
`disable-model-invocation` / `user-invocable` 被丢弃。现在：

| frontmatter | 解析结果 | 注册行为 |
|---|---|---|
| `disable-model-invocation: true` | `modelInvocable: false` | 传 `invocation.modelInvocable=false` |
| `user-invocable: false` | `userInvocable: false` | 传 `invocation.userInvocable=false` |
| **两键都缺** | `invocationDeclared` 未设 | **不传** `invocation`（交官方默认） |

**缺键不传**是有意的：两键默认即 true（KB `skills.md:132`）。若缺键仍传
`{both true}`，就把「用户没表态」写死成「用户表过态」，未来官方改默认值时本插件会悄悄分叉。

### 3.2 可见性回读（`classifySkillVisibility`）

注册后 fire-and-forget 调一次 `ctx.skills.snapshot()`，分类三态：

| 条件 | 裁决 | 理由 |
|---|---|---|
| `snap === null`（宿主无 snapshot/旧代/抛错） | `unknown` | 采不到 ≠ 缺失 |
| `snap.complete === false` | `unknown` | 官方：不完整观测不可下结论 |
| 命中 `name` | `active` | 附带 `source`/`provider` 分辨谁赢了同名 |
| 未命中且 `complete` | `absent` | 点名「可能被 project 层同名压制」 |

**绝不**把 `unknown` 谎报成 `absent`：工作区安装态会被误判成缺失。

`index.ts` 把结论写入 `recordSkillVisibility`（`src/host/runtime/skillVisibilityState.ts`）——
**状态**而非日志，因为读者问的是「**现在**模型能不能看见」，不是「历史上发生过什么」。

### 3.3 `skills/change` 观测对称

`src/host/runtime/skillsChangeCounter.ts` 与 `toolsChangeCounter.ts` 同构（零依赖叶子）。
官方契约：事件**不带 diff**，消费方自行重取 snapshot（KB `skills.md:340-352`）
⇒ 只计数，**不缓存目录**（缓存会变成第二真相源）。

`wireSkillsChange` 在宿主无 `ctx.on` 时返回 `false`，不制造假监听。

## 4. 内部技能库：从「零引用」到「被读、可判红」

### 4.1 修前的事实

| 事实 | 取证 |
|---|---|
| `assets/skills/` 有 1 主干 + 9 叶 + 1 元技能 + 注册表 `skills.index.json` + 三脚本 | `assets/skills/README.md` |
| **`src/` 对 `skills.index.json` 的引用数 = 0** | cycle-107 审计（研究输入 L） |
| 闭环体检第四族只扫 `assets/skill/scripts/*.mjs`（**主干**脚本） | `src/host/closureAudit/skillClosure.ts:33` |
| ⇒ 整个库不在任何扫描面内 | 同上 |

后果：库是否完整、是否漂移，只能靠人记得跑一次 `skill-lib-manifest.mjs` ——
而「只在人记得时成立」的检查等于没有检查。

### 4.2 现在谁读它

| 层 | 落点 | 职责 |
|---|---|---|
| 读数 | `src/host/runtime/skillLibrary.ts` | **只读**对账：注册表条目 ⇄ 目录 / `SKILL.md` / `anchors`，反向查未登记目录 |
| HTTP | `GET /anic/skill/health` 的 `library` 段 | 面板与外部工具可查 |
| LLM | `anic_status` 的 `skillLibrary` 字段 | 模型能看到「库有几条、有没有问题」 |
| 守卫 | `tests/contract/skillLibraryRegistryContract.test.ts` | 真实库上 `issues === []`、条目 ≥10、每个 SKILL.md/anchors 全在；并断言 `src` 真的读了注册表 |

### 4.3 六种 issue（补救动作不同，不可合并）

| kind | 含义 | 补救 |
|---|---|---|
| `registry-absent` | 库根/注册表不在 | 装包缺资产 |
| `registry-parse` | JSON 损坏或条目缺 `name`/`dir` | 修表 |
| `missing-dir` | 条目声明的目录不在 | 补目录或改表 |
| `missing-skill-md` | 目录在但缺 `SKILL.md` | 补文件 |
| `missing-anchor` | 声明的锚点文件不在 | 补文件或改表 |
| `unregistered-dir` | 磁盘有目录但注册表没登记（幽灵技能） | 改表 |

**首跑即抓到的真实缺陷**：`skills.index.json` 的 10 条里 **9 条缺 `dir` 字段**
（只有 `_meta/skill-library-evolution` 有）。机器面因此只能识别 1 个技能。
这正是一个「没有任何断言覆盖就会永远存在」的漂移 —— 现在它有一条会判红的契约。

> 设计取舍：`dir` **不从 `name` 派生**。注册表是唯一事实源，派生会让「表缺字段」
> 永久隐身。缺字段就报 `registry-parse`，逼人补表。

### 4.4 为什么复用 `skill-lib-manifest.mjs` 而不重写

那是 **skill 侧**脚本（写文件、有 CLI、负责「生成/修」）；插件运行时需要的是
**只读、幂等、无副作用**的读数（负责「读/判」）。脚本会写注册表，
**运行时绝不能自动改项目事实**。两边口径同源、职责分离，一致性由上面的契约钉住。

## 7. 为什么不采用研究输入里的替代方案

| 替代 | 否决理由 |
|---|---|
| 用 `deferLoading` 做披露 | 它是**注册期/全局**属性；本插件单实例服务多工作区，需要 **per-agent scope** 的 `restrict`。已由 `docs/agents/渐进式披露与轻量索引设计.md` 与 `nativeDeferLoadingContract` 双向钉死 |
| 给工具加 `availability: resident\|discoverable` | **不是官方字段**（KB `tools.md:31-107` 无此字段），宿主不读。加了就是「声明无消费方」 |
| 抄 ops 的 `tools.view()` | 该 API **不在 KB 任何页面**（`site/reference` 全量 grep 命中 0）。本仓不调 `schemas()`，无深拷贝成本；唯一需要的读面是文档化 `schemas(scope)` |
| 把 `assets/skills/` 改成 `registerProvider` | 收益真实，但要实现 `list/get/rank/locator/signal` 并处理 watcher/失效，属**新子系统**而非补丁。先把回读通路与读数打通 |
