1. `.anic-manifest.json`（`src/host/skillIntegrity.ts:22-36`）——技能**完整性**清单

## 2. 对照既有渐进式披露先例

### 2.1 官方先例：ToolSearch = `ctx.tools.restrict()`

**这是本设计最重要的外部依据**。DSH 官方扩展手册把该机制**逐字命名为**
「ToolSearch / 渐进式披露」（KB `site/reference/cookbook/extension-cookbook.md:123`）：

> | ToolSearch / 渐进式披露 | 当可见集变化时替换一个作用域化的 `ctx.tools.restrict()` 注册；注册表保持展示、查找和执行三者对齐 |

同文件 :109 给出选用纪律：
> 对于需要在**展示、查找和执行之间保持对齐**的工具过滤，**优先使用 `ctx.tools.restrict()`**。

官方 API 形状（KB `site/reference/subsystems/tools.md`，全部实测读出）：

| 机制 | 锚点 | 语义（原文要点） |
|---|---|---|
| `register(definition)` | KB subsystems/tools.md:534 | 全局或调用方 scope 注册；**returns the exact disposer that unregisters the tool** |
| `restrict(filter)` | KB subsystems/tools.md:543 | 为**调用方 scope** 限制全局工具；`allow`/`deny` 掩码；**restrictions intersect**；scope-local 注册仍可见；**returns the exact disposer that lifts this restriction** |
| `schemas(scope)` | KB subsystems/tools.md:574 | 把可见 definition 投影到 allowlist 的模型面字段（`name/description/parameters`），**排除 execute/presentation 回调** |
| `get(name, scope)` | KB subsystems/tools.md:566 | 按 scope 查找（scoped shadows global；被 restrict 掉的 global **reads as absent**） |
| `execute(exec)` | KB subsystems/tools.md:599 | 不可见工具报 **`UNKNOWN_TOOL`** |
| `tools/change` | KB subsystems/tools.md:614-626 | 「A tool was registered or unregistered, or a scoped restriction changed」——**UNFILTERED** 通知，全局变更关系到每个 agent 的下一次装配 |

**可借鉴的三段机制**（与本需求逐字对应）：

1. **索引 →** 用一个**恒在**的读工具给出 `{id, summary, domain}`（≈1.9 KB）；
2. **按需取 schema →** 一个取工具返回目标工具的**完整** `parameters`（精确，非摘要）；
3. **激活 →** `restrict` 的 **disposer 被 replace**，可见集变化，`tools/change` 触发下一次装配。

**关键可行性**：`restrict` 与 `register` 都**返回 disposer**——「激活/停用」天然是
**注册生命周期**操作，可被 `ctx.effect` 托管、随 HMR 清理，不需要自造状态机。

### 2.2 MCP 侧 `tool_search`/`tool_detail` 形态

本仓**自己的技能包**就是该形态的现成样本：
`assets/skill/scripts/mcp-server.mjs`（449 行）经 `ListToolsRequestSchema`
（:151）一次声明 **15 个** MCP tools，总块 **7,403 B**，descriptions 合计 2,994 字符。

**但本仓的 MCP server 是「一次全量声明」，不是渐进式披露**——它没有 search/detail 两级。
真正可借鉴的是**宿主自身的 MCP 连接器**形态（本会话 SDK 可见）：`tool_search` /
`tool_detail` 在「最后一次成功工具缓存」里只返回**能力元数据**，
**不调用目标工具、不读调用参数/结果/凭据**，且激活必须 `preview-activate` +
用户显式确认后在**下一次模型推理边界**生效。

**抽出三条可直接搬到 DSH 插件的机制**：

| MCP 侧机制 | DSH 侧对应物 | 可行性 |
|---|---|---|
| 索引只给元数据，不给你 schema | `anic_tools_search` 返回 `{id,summary,domain}` | ✅ 纯读，零风险 |
| `tool_detail` 取单工具精确 schema | `anic_tool_detail` 返回**源码投影**的 `parameters` | ✅ 但会**临时**增加上下文 |
| 激活边界 = 「下一次推理边界」 | `restrict()` disposer 替换 + `tools/change` | ⚠️ **未验证**（见 §3.4 边界） |
| 激活需显式确认 | 首次激活写 FlowTracker / 落审计 | ✅ 复用现有记账面 |

### 2.3 技能面先例

## 3. 目标形态（可验收设计）

### 3.1 索引资产格式

新增 **单一事实源投影**（沿用 `toolIds.ts` 的耦合方向纪律：**真相在注册处**）：

```
// 两份都是生成物（可重建，不手写；失效策略见 §3.3）

assets/index/capability-index.json     ← ① 注入面（进上下文，必须极简）  实测 1,491 B
{ "v": 1, "commit": "601c62b",
  "tools":   [ ["anic_evaluate", "跑 E1-E8 评估并写评估报告"],
               ["anic_skill",    "按白名单直调技能脚本"] ],
  "scripts": [ "eval-runner", "gate-check", "quick-validate", ... ] }   ← 15 个裸名

assets/index/capability-hashes.json    ← ② 非注入面（**不进上下文**）    实测 678 B
{ "v": 1, "commit": "601c62b",
  "hashes": { "anic_evaluate": "sha256:<canonical description+parameters>", ... } }
```

**体积实测（本轮真算了，纠正初稿的估算错误）**：

初稿曾估算「≈3.6 KB」。实测**不成立**——把 `domain`/`writeSide`/`schemaHash`(`sha256:`+64 hex = 71 B × 19)
与 `purpose`/`positional` 一起写进**同一份**索引，canonical JSON 达 **8,757 B**，
相对基线 11,738 B 只减 **25.4%**（叠加载器后仅 14.8%）。**根因：71 B 的十六进制哈希 ×19 ≈ 1,350 B，
再加 `domain`/`writeSide` 字段 ≈ 1,100 B——元数据比摘要还贵。**

**纠正后的形态**（把校验面从注入面里拆出去）：

| 变体 | 模型可见字节 | 占基线 |
|---|---|---|
| 初稿（含 hash/domain/writeSide） | 8,757 | 74.6%（不可接受） |
| `id` + 40 字符摘要 + 脚本裸名 | **1,491** | **12.7%**（选定） |
| 仅 `id` + 脚本裸名（最瘦） | 636 | 5.4% |

**选定 `id` + 40 字符摘要**：1,491 B 是「模型能据此选工具」的下限——
再往下（仅 id）模型只能靠名字猜语义，发现率会塌。

**格式纪律**：
- **绝不含 `parameters` 与完整 description**——含则收益归零（§1.1 证明 params 占 47%）。
- `summary` 与注册处的 `description` **语义不同**：description 是**触发条件**（SDO 纪律，
  `src/host/tools.ts:59-60`），summary 是**能力语**。二者不得互相自动派生——
  **派生会破坏 trigger-eval 的区分度**（`tests/unit/triggerEvalContract.test.ts:74-79`，
  24/24 recall / FPR 0/14），summary 一旦被误用为 description 就是回归。
- `schemaHash` **不进注入面**——它在 `capability-hashes.json` 里供 §3.3 失效判据与
  §4/A5 的「索引⇄源码一致」验收使用。**原则：模型要用什么才进上下文，校验用的东西不进。**
- `domain`/`writeSide`/`positional` 等**元数据不进注入面**（实测它们比摘要还贵）。
  模型需要「某工具写不写盘」时，由 §2 的取详情工具在**按需**时回答，而非预先付费 ×19。

### 3.2 加载时机

| 资产 | 通道 | 时机 | 成本 |
|---|---|---|---|
| 工具索引 | **插件自有的 system prompt section**（`ctx.systemPrompt.section()`，KB site/reference/cookbook/extension-cookbook.md:119） | 会话装配，**恒在** | **1,491 B**（实测） |
| 工具完整 schema | `restrict()` 的可见集 | **激活后** | 激活前 **0** |
| 技能脚本索引 | 同上 section 的一节 | 会话装配 | **含在 1,491 B 内** |
| 校验哈希 sidecar | 插件内部读，**不进上下文** | 失效判定时 | **0**（678 B 落盘） |
| 技能正文 | 官方 `skill({name})` | 调用时 | 20.9 KB（**已实现**） |
| references 单篇 | 模型自己 read | 需要时 | **已实现**（缺索引） |

**收益估算**（19 工具）：

```
现状：  11,738 B（schema 全量，实测）
目标：   1,491 B（索引，实测） + 513 B（2 个加载器工具，实测）= 2,004 B
净减：   9,734 B ≈ **82.9%**（比值 0.171）
单工具成本：618 B → **78 B**（约 8×）
```

**加载器工具实测**（按本仓最瘦的既有工具形状构造）：
`anic_tool_detail` **269 B** · `anic_tools_search` **244 B**——两者都远小于均值 618 B，
因为它们的 `parameters` 只有一个 string 字段。

### 3.3 失效 / 版本策略

三级失效，**全部 fail-closed 到 full 模式**（绝不 fail-closed 到「零工具」）：

1. **内容失效**：`capability-hashes.json` 里逐工具的 `schemaHash` 与**从源码重算**的
   canonical `description+parameters` 不符 → 该条索引作废，**退回 full**。
   （哈希 sidecar **不进上下文**，因此可以逐条精确比对而不付费。）
2. **版本失效**：两份资产都记 `commit`；与 HEAD 不符 → 标记 stale，
   **退回 full** 并记日志（scoped logger，不直连 console）。
3. **宿主能力失效**：宿主无 `ctx.tools.restrict`（旧代/stub）→ **退回 full**。
   多代防御沿用现有纪律：`ctx.get(name, false)` 探测存在性
   （CLAUDE.md：「`ctx.get(name)` 默认 strict=true 会杀死正在 loading 的 provider」）。

**绝不做**的事：索引缺失时**猜测** schema、或静默把 19 个工具藏成 0 个
（后者属 CLAUDE.md 反复收口的**静默降级**形态）。

### 关键设计发现（cycle-74 源码取证）：宿主有**原生** deferLoading，但它**不适合本场景**

在真实安装包 `app.asar`（dsh 0.2.1-rc.2）内取证到宿主**原生**渐进式披露机制：

```ts
// dsh-llm ToolSchema（llm-streaming.md:704-710）逐字注释：
interface ToolSchema {
  /**
   * Requests deferred loading of the tool definition into model context,
   * independently of whether a tool-addition block records the tool.
   * Uses Anthropic's defer_loading terminology.
   */
  deferLoading?: true
  name: string; description: string; parameters: Record<string, unknown>
}
```

接收面实测（`dsh-tools/lib/index.js` `register`）：宿主注册时**只**校验 `output` 与 `timeoutMs`，
其余字段原样收下；`schemaOf` 解构 `{name,description,parameters,deferLoading}`，
仅当 `deferLoading === true` 时把它放进模型 schema。

**为什么本场景不能用它（决定性）**：

| 维度 | `deferLoading` | `restrict` |
|---|---|---|
| 作用域 | **注册期 / 全局**（写在 ToolDefinition 上） | **per-agent-scope**（写在 scoped ctx 上） |
| 本插件的现实 | 单实例服务**多工作区会话** | 每个会话有自己的 agent scope |
| 结论 | 全局延迟 = 影响**所有**工作区，无法表达「A 项目 indexed、B 项目 full」 | ✅ 正好表达 per-workspace 披露 |

⇒ **per-workspace 的渐进式披露必须走 `restrict` + agent 生命周期接线**（即下一轮 intent）。
`deferLoading` 只适合「本插件工具在所有场景一律延迟」的静态选择，与本设计的配置化目标不符。

**已落地的一处契约补全**：`src/host/toolsSlot.ts` 的 `ToolRegistration` 补上 `deferLoading?: true`
并写明官方语义与接收面——此前本仓契约缺该字段，属「宿主支持但插件不知道」的盲区；
补上后未来若要用静态模式可直接用，且**不影响任何既有行为**（默认不设该字段）。
